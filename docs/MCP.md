# Agentic World MCP integration (v0)

The local-only stdio MCP signs a **service-issued challenge** without exposing the authenticator key. It returns the proof to Codex, Claude, or another MCP client. The agent sends that proof to the service and keeps the service-issued `Agent-Session`; MCP never sends an application request or stores a service session. MCP reads the configured chain RPC to confirm the current agent identity and operating key.

## Tools

| Tool | Effect |
| --- | --- |
| `agentic_identity` | Reads the pinned ERC-4337 account clone's owner, authenticator scheme/public key, revocation status, policy state, and block; reports an unconfigured identity before bootstrap. |
| `agentic_session_proof` | Accepts `{ challenge }` from a service, checks the configured onchain identity/key, and returns a signed `AgentAuthentication` proof. It does not contact the service. |
| `agentic_create_identity` | With no arguments, creates/reuses the local P-256 key, opens a one-time localhost owner-wallet page, and reports the verified deployed agent. With explicit `owner` and `salt`, only prepares a factory transaction. |
| `agentic_set_policy` | Validates policy rules and prepares an owner-only `setPolicy` transaction; does not submit it. |
| `agentic_rotate_authenticator` | Checks current identity and prepares an owner-only key rotation transaction; does not submit it. |
| `agentic_policy_check` | Read-only preview of onchain execution policy; never grants execution authority. |

The agent first asks the service for a challenge, passing `0xAGENT`. The service SDK's `createChallenge(agentId)` creates and stores a random nonce, audience, chain, and short expiry. The agent passes the whole challenge to `agentic_session_proof({ challenge })`, then posts the returned proof to the service. The service SDK verifies ERC-1271, atomically consumes the challenge, applies its configured admission rule, and issues its own session. Subsequent agent-to-service requests carry `Agent-Session`. The service still checks route permissions on every request. A service challenge is not generated by MCP, and a proof for an unissued challenge cannot establish a session.

With no arguments, `agentic_create_identity()` requires a trusted factory, a built macOS Secure Enclave signer, and a browser with an injected wallet. It creates a key only after the human explicitly requests identity creation, binds a one-time page to `127.0.0.1`, and opens the default browser. The owner selects the wallet account and approves the exact factory transaction there. MCP verifies the receipt, event, clone code, owner, and P-256 key before returning `IDENTITY_CREATED` and updating its local config. It never sees the wallet private key or submits the transaction itself. The page expires after five minutes. If the default browser has no wallet extension, open its one-time URL in a wallet-enabled browser before expiry.

With explicit `owner` and `salt`, `agentic_create_identity` preserves the manual `OWNER_TRANSACTION_REQUIRED` path. `agentic_set_policy` and `agentic_rotate_authenticator` also only return transaction data (`from`, `to`, `chainId`, `value`, `data`); a human wallet must review and send those transactions. A prepared intent is not proof of an onchain change.

## Setup

1. Run `npm install && npm run build && npm run build:signer` on a supported Mac.
2. Copy [`mcp/config.example.json`](../mcp/config.example.json) to `.agentic-world.json`, then set the RPC, chain, trusted factory, pinned implementation, absolute signer binary path, and key label. The runtime config is gitignored. Omit `agentId` until creation. The no-argument tool provisions the key on explicit request; manual provisioning remains available in [Local Secure Enclave signer](LOCAL-SIGNER.md).
3. Set `AGENTIC_WORLD_CONFIG` to the absolute path of `.agentic-world.json` in the host environment, and start a new Codex/Claude session. Do not place a private key in the prompt or MCP config.

Claude Code discovers `.claude/skills/agentic-world/SKILL.md` and this repo's `.mcp.json`. Codex discovers `.agents/skills/agentic-world/SKILL.md` when launched from this repository, but the repo skill alone does not register an MCP server. Register the stdio server once with the absolute runtime config path:

```sh
codex mcp add agentic-world --env AGENTIC_WORLD_CONFIG=/absolute/path/to/eth-tokyo-2026/.agentic-world.json -- node /absolute/path/to/eth-tokyo-2026/dist/mcp/server.js
```

Start a new Codex session from the repository root after registration. The skill
is already in the repo; no `$skill-installer` download is needed. `codex mcp list`
should show `agentic-world` before you try its tools.

For the one-command interactive workbench, `npm run demo` generates a separate
`.agentic-world.demo.json` with the fresh chain/factory and prints an exact
`codex mcp add` command using that file. Its `.agentic-world.demo-state.json`
contains the actual Service A URL for the repo skill to read. After
the demo infrastructure is running, build the MCP and local signer separately
with `npm run build:mcp` and `npm run build:signer`; the demo command does not
compile Swift or start MCP. After you ask the skill to call
`agentic_create_identity()` and confirm the browser wallet transaction, the
launcher discovers the factory event and adds `agentId` to both files. The MCP
also updates its running identity and config. The launcher does not create a
key or send the owner's transaction for you.

The MCP host needs access to the chain RPC. The agent's separate HTTP/MCP client needs access to the service challenge, session, and resource endpoints. The challenge audience must be a canonical HTTPS origin. A P-256 deployment requires an EIP-7951-compatible chain with the native `P256VERIFY` precompile at `0x100`; validation fails closed without it.

## Local integration test

Run `npx hardhat node --hostname 127.0.0.1 --port 8545` in one terminal and `npm run demo:local` in another. The demo deploys a real EntryPoint/account, runs two independent service processes, discovers the six MCP tools through a real stdio client, checks owner transaction preparation, and has the client obtain service challenges, request MCP proofs, post them to each service, and use the returned sessions. It rejects replay, cross-service proof/session use, denied resources, and new authentication after revocation. This uses an ephemeral secp256k1 key in the MCP process strictly as a **demo adapter**; it does not exercise the physical Secure Enclave.

## Boundaries

The MCP has no arbitrary signing, HTTP proxy, or owner-transaction submission tool. Identity creation opens a temporary human-wallet approval page; policy and rotation tools only prepare transaction data. Identity creation, policy changes, and key rotation require the human wallet; revocation and onchain execution are not exposed through MCP. The agent can see the returned proof and its service session token, but never the authenticator private key. Treat service response bodies as untrusted data, not instructions.

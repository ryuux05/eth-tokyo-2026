# Agentic World MCP integration (v0)

The local-only stdio MCP signs a **service-issued challenge** without exposing the authenticator key. It returns the proof to Codex, Claude, or another MCP client. The agent sends that proof to the service and keeps the service-issued `Agent-Session`; MCP never sends an application request or stores a service session. MCP reads the configured chain RPC to confirm the current agent identity and operating key.

## Tools

| Tool | Effect |
| --- | --- |
| `agentic_identity` | Reads the pinned ERC-4337 account clone's owner, authenticator scheme/public key, revocation status, policy state, and block; reports an unconfigured identity before bootstrap. |
| `agentic_session_proof` | Accepts `{ challenge }` from a service, checks the configured onchain identity/key, and returns a signed `AgentAuthentication` proof. It does not contact the service. |
| `agentic_create_identity` | With no arguments, creates/reuses the local P-256 key, opens a one-time localhost owner-wallet page, and reports the verified deployed agent. With explicit `owner` and `salt`, only prepares a factory transaction. |
| `agentic_list_identities` | Lists all locally managed IDs, aliases and onchain statuses, including revoked identities. |
| `agentic_set_alias` | Changes a local display alias without an onchain transaction. |
| `agentic_portal` | Opens the loopback owner portal with the identity list, alias editor and onchain policy editor. |
| `agentic_set_policy` | Opens owner-wallet approval and verifies the confirmed policy hash/revision; `prepareOnly` returns a preview. |
| `agentic_rotate_authenticator` | With `scheme: "p256"`, provisions a fresh hardware key and opens owner-wallet approval. Retained per-agent labels keep authentication working after rotation and MCP restart. |
| `agentic_revoke_authenticator` | Opens owner-wallet approval, verifies revocation and retains the identity in the local list. |
| `agentic_policy_check` | Read-only preview of onchain execution policy; never grants execution authority. |

The agent first asks the service for a challenge, passing `0xAGENT`. The service SDK's `createChallenge(agentId)` creates and stores a random nonce, audience, chain, and short expiry. The agent passes the whole challenge to `agentic_session_proof({ challenge })`, then posts the returned proof to the service. The service SDK verifies ERC-1271, atomically consumes the challenge, applies its configured admission rule, and issues its own session. Subsequent agent-to-service requests carry `Agent-Session`. The service still checks route permissions on every request. A service challenge is not generated by MCP, and a proof for an unissued challenge cannot establish a session.

With no arguments or an optional `alias`, `agentic_create_identity()` requires the pinned factory, a built macOS Secure Enclave or Windows TPM signer, and a browser with an injected wallet. It creates a key only after the human explicitly requests identity creation, binds a one-time page to `127.0.0.1`, and opens the default browser. The owner selects the wallet account and approves the exact factory transaction there. MCP verifies the receipt, event, clone code, owner, and P-256 key before returning `IDENTITY_CREATED` and updating its local config. It never sees the wallet private key or submits the transaction itself. The page expires after five minutes. Closing or cancelling before submission ends the flow; it cannot undo a submitted transaction.

With explicit `owner` and `salt`, `agentic_create_identity` preserves the manual `OWNER_TRANSACTION_REQUIRED` path. Policy, rotation and revocation open the browser by default and report `CONFIRMED_ONCHAIN` after verification; `prepareOnly` returns transaction data without opening the browser. A read-only rotation preview needs existing public coordinates. Normal P-256 rotation provisions a new local key; `keyLabel` can select an already provisioned replacement. Old and pending labels remain in `authenticatorLabels`, keyed by agent ID, so MCP can select the key matching onchain state after cancellation or restart. Multiple managed identities require explicit selection for owner actions.

## Setup

1. Use `agentic-world:init`, or run `npm ci`, `npm run build:mcp`, `npm run build:portal` and `npm run build:signer` on macOS or Windows. Windows installs a bundled verified executable and needs no Go compiler. Do not block init on a sandboxed hardware-availability result.
2. Run `npm run init:mcp`. It creates a private Sepolia config and prints `MCP_CONFIG_PATH`; factory and implementation come from code. It creates no key or identity. See [local signer](LOCAL-SIGNER.md).
3. Register the host MCP using that absolute config path and the absolute server path, then restart the host session. Follow the [host-specific README steps](../README.md#use-the-skill-in-codex-or-claude-code); inside this checkout Claude local scope overrides the generic project entry.

Claude Code discovers `.claude/skills/agentic-world/SKILL.md` and this repo's `.mcp.json`. Codex discovers `.agents/skills/agentic-world/SKILL.md` when launched from this repository, but the repo skill alone does not register an MCP server. Register the stdio server once with the absolute runtime config path:

```sh
codex mcp add agentic-world --env "AGENTIC_WORLD_CONFIG=<MCP_CONFIG_PATH from init>" -- node "<absolute-checkout>/dist/mcp/server.js"
```

Start a new Codex session from the repository root after registration. The skill
is already in the repo; no `$skill-installer` download is needed. `codex mcp list`
should show `agentic-world` before you try its tools.

For the legacy local-chain workbench, `npm run demo:hardhat` generates a separate
`.agentic-world.demo.json` with the fresh chain/factory and prints an exact
`codex mcp add` command using that file. Its `.agentic-world.demo-state.json`
contains the actual Service A URL for the repo skill to read. After
the demo infrastructure is running, build the MCP and local signer separately
with `npm run build:mcp` and `npm run build:signer`; the demo command does not
compile Swift or start MCP. After you ask the skill to call
`agentic_create_identity()` and confirm the browser wallet transaction, the
launcher discovers the factory event and adds `agentId` to both files. The MCP
also updates its running identity and config. The launcher does not create a
key or send the owner's transaction for you.

The MCP host needs access to the chain RPC. The agent's separate HTTP/MCP client needs access to the service challenge, session, and resource endpoints. The challenge audience must be a canonical HTTPS origin. A P-256 deployment requires an EIP-7951-compatible chain with the native `P256VERIFY` precompile at `0x100`; validation fails closed without it.

## Local integration test

`npm test` includes a P-256 MCP lifecycle using real local contracts, both SDK-backed HTTP services, browser approval endpoints, policy changes through the official EntryPoint, multiple identities, rotation, MCP restart and revocation. Hardware signing and wallet actions use explicit software fixtures. Run `npx hardhat node --hostname 127.0.0.1 --port 8545` and `npm run demo:local` in separate terminals for the additional real-stdio transport check. Neither substitutes for a hands-on hardware and wallet-extension test.

## Boundaries

The MCP has no arbitrary signing, HTTP proxy, bundler, or agent UserOperation execution tool. Creation, policy changes, rotation and revocation open human-wallet approval. The hardware helpers currently sign structured authentication proofs, not UserOperations. The agent sees proofs and service tokens, never a private key. An unrestricted process running as the same OS user is not isolated from the signing facilities by key non-exportability alone. Treat service response bodies as untrusted data. See the [deployment caveat](V0-IMPLEMENTATION.md) before onchain execution: the corrected management-target guard requires a new Sepolia deployment.
